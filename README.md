# ЛР1 — backprop руками


Файли: `data.py` (завантаження і підготовка Iris), `model.py` (forward, крос-ентропія, backward), `torch_reference.py` (та сама мережа в PyTorch для звірки), `checks.py` (порівняння і чисельна перевірка), `main.py` (запуск всього; `--bug` вмикає зламану версію з п.4).

## Дані

Кожен клас перемішую окремо через `np.random.default_rng(0)`, перші 35 індексів у трейн, решта 15 у тест — виходить 105/45 стратифіковано. Mean і std (ddof=0) рахую тільки по трейну і тими самими числами стандартизую тест.

## Мережа

X(4) -> Linear -> ReLU -> Linear -> логіти(3). W1 (4x8) — He, std = sqrt(2/4), W2 (8x3) — Xavier, std = sqrt(2/(8+3)), біаси нульові. Обидві матриці генеруються одним rng(0) по черзі (W1, потім W2), інакше числа не зійдуться з тим, що очікує перевірка.

## Прямий прохід і втрата

```
Z1 = X@W1 + b1     (N,8)
A1 = relu(Z1)      (N,8)
Z2 = A1@W2 + b2    (N,3)   -- логіти
```

Крос-ентропія через log-softmax зі зсувом на максимум (інакше exp вибухає):

```
m = max(Z2, по класах)
log_softmax = Z2 - m - log(sum(exp(Z2-m)))
loss = -mean(log_softmax[i, y_i])
```

Для backward зберігаю X, Z1, A1 (в коді ще Z2, хоча він там особливо і не потрібен). X іде в dW1, Z1 потрібен щоб зробити маску ReLU, A1 — в dW2. Без них рахувати backward нема з чого.

## Backward

dZ2 = (softmax(Z2) - onehot(y)) / N, розмір (N,3) — це похідна втрати по логітах, звідси все й тягнеться.

```
dW2 = A1.T @ dZ2          (8,3)
db2 = sum(dZ2)             (3,)

dA1 = dZ2 @ W2.T           (N,8)
dZ1 = dA1 * (Z1>0)         (N,8)

dW1 = X.T @ dZ1            (4,8)
db1 = sum(dZ1)              (8,)
```

Маска `(Z1>0)` тут ключова: похідна ReLU дорівнює 1 там де вхід був додатний і 0 інакше, і без цього градієнт піде туди, куди не треба.

## Звірка з PyTorch

`torch.nn.Linear` зберігає ваги `(out, in)`, тому W1/W2 при копіюванні транспоную. Все у float64, на повній вибірці (105) і початкових вагах: loss numpy = `1.4562007801142816`, loss pytorch = `1.4562007801142818`.

| Величина | макс. \|NumPy-PyTorch\| | пройдено |
|---|---|---|
| Втрата | 2.220e-16 | так |
| Градієнт W1 | 5.551e-17 | так |
| Градієнт b1 | 3.643e-17 | так |
| Градієнт W2 | 8.327e-17 | так |
| Градієнт b2 | 1.388e-16 | так |

Це рівень машинної похибки float64, поріг 1e-12 проходить з великим запасом.

## Чисельна перевірка

eps = 1e-6, центральна різниця, для W1[0,0], b1[0], W2[0,0], b2[0]:

| Параметр | backward() | чисельна | різниця | пройдено |
|---|---|---|---|---|
| W1[0,0] | -0.0199201843 | -0.0199201844 | 6.0e-11 | так |
| b1[0] | -0.0705661116 | -0.0705661116 | 3.6e-11 | так |
| W2[0,0] | 0.1352302086 | 0.1352302087 | 9.2e-11 | так |
| b2[0] | 0.0855216448 | 0.0855216450 | 1.5e-10 | так |

Поріг 1e-7, тут теж все впевнено проходить.

## Дослід з помилкою

Прибираю ділення `dZ2 /= n` в backward (прапорець `divide_by_n=False`, лишаю функцію втрат як є).

Прогноз до запуску: втрата не зміниться (вона рахується окремо і не знає про backward), усі ненульові градієнти виростуть рівно у 105 разів (n трейну), бо все далі йде лінійно від dZ2 — і саме звірка з PyTorch та чисельна перевірка мають це виявити, а перевірка втрати нічого не покаже.

Так і вийшло. Loss не змінився взагалі (різниця 0), `dW1_bug/dW1 = 105.00000000000001` при n=105. Звірка з PyTorch на зламаній версії дає різниці порядку 10-30 замість 1e-16 (не проходить), чисельна перевірка — різниці 2-14 замість 1e-10 (теж не проходить). Тобто помилку ловлять обидві перевірки градієнтів, а перевірка втрати — ні, саме як і передбачалось. Ваги під час досліду ніде не змінювались, після нього коректна версія (default) лишається робочою.

## Висновок

Ручний backward збігається і з PyTorch, і з чисельним диференціюванням з великим запасом, формули порахував правильно. Дослід показав, що конкретна помилка в одному місці backward (пропущене ділення) пропорційно масштабує всі градієнти і не чіпає loss — і що саме звірка градієнтів, а не перевірка loss, ловить такі речі.
